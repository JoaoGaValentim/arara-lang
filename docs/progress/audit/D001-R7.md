## B. Acceptance inconsistency and correction

### B.1 What was contradictory

`D001-R6.md` §K asserted that every Directive 001-R6 §8 condition was satisfied,
including a row reading "Mandatory ledger reconciliation completed — see §I". §I
said the opposite: the ledger still described the development branch and
reconciliation was outstanding. Two sections of the same document made incompatible
claims, and the operator-facing summary inherited the optimistic one.

`DECISIONS.md` `D001-24` repeated the error in its "Conditions satisfied" list.

### B.2 Root cause

The defect was a conflation of three different facts:

1. **Contract acceptance** — an owner decision.
2. **Integration** — a Git operation with a verifiable merge commit.
3. **Recovery-ledger reconciliation** — bookkeeping about which branch the ledger
   describes.

Only the first two were complete. Treating the third as satisfied because the first
two were is how a summary becomes false without anyone writing a deliberate lie.

### B.3 Correction

Acceptance, integration, and reconciliation are now recorded separately, and the
reconciliation is marked as having been outstanding at acceptance time and closed
under this directive.

| Document | Correction |
| --- | --- |
| `D001-R6.md` §K | Conditions split into per-category rows; the reconciliation row reads **OUTSTANDING at R6 — completed in R7** |
| `DECISIONS.md` `D001-24` | "Conditions, stated by category" replaces the flat satisfied list; a correction note preserves what was claimed and why it was wrong |
| `GATES.md` verdict | Three-fact table; no gate criterion referenced the ledger, which is why the gap did not block acceptance |
| `STATE.md` | Rebuilt as a post-merge snapshot with the three-way separation in §4 |
| `CONTINUATION.md` | The same three facts, stated first, with the snapshot rule |

`D001-13`–`D001-23` are untouched. `D001-24` is preserved as the owner's acceptance
decision; only its factual claim about prerequisites is corrected, and the
correction is labelled rather than silently dropped.

### B.4 A second error found and corrected

While verifying the baseline, §I's claim "`git merge-base main HEAD` is `5441a9f`"
proved false. The real relation:

```text
merge-base(origin/main, HEAD) = b0c2492eec39a3ae8877f70d6607afcc3dd128fa
git merge-base --is-ancestor origin/main HEAD  ->  false
```

The branch continues from `b0c2492`, the reviewed tip of PR #1, not from the merge
commit. The merge is still clean, but for a different reason: `b0c2492` is **parent
2** of `5441a9f`, and both trees are `9536279f…`, so the merge changed no content.

This mattered. A merge-base assertion is what a reviewer uses to decide whether an
integration is safe, and the original claim implied the branch already contained the
merge. It is corrected in `D001-R6.md` §I with the failing command and its output
shown.

Class: `VERIFIED` for both corrections; `FAILED` for the two original claims.

## C. Recovery-ledger reconciliation evidence

### C.1 Structure

`STATE.md` now separates the three things Directive 001-R7 §4 names:

| Concern | Ledger field | Meaning |
| --- | --- | --- |
| Git revision observed at verification | `mainline_merge_commit`, `mainline_merge_parents`, `mainline_tree`, `mainline_observed_at` | A historical snapshot of `main` |
| Branch the ledger is committed on | `ledger_branch`, `last_verified_commit` | Where this document lives and which commit precedes it |
| Current branch and HEAD at recovery | none — deliberately absent | Discovered live from `.git`; never stored |

The absence of the third is a design decision, stated in `live_state_rule`. Storing

### C.3 The rule that keeps the snapshot honest

`mainline_snapshot_rule` states that the recorded revision is what was observed, not
an assertion about the current tip, and that a later `main` does not falsify it.
The only hard invariant is ancestry. A divergence where the snapshot is **not** an
ancestor is a rewrite or a wrong repository and must be reported as a failure.

This preserves `G9-A` as ratified by `D001-11`: the ledger records the commit
preceding itself and verifiable Git state, and nothing here reintroduces the
impossible self-reference.
