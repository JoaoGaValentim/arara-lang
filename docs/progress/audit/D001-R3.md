## 3. Java 21 naming analysis

### 3.1 The count was wrong

JLS 21 §3.9 states in prose: *"51 character sequences ... are reserved for use as
keywords and cannot be used as identifiers"*, and *"Another 17 character sequences
... may be interpreted as keywords or as other tokens, depending on the
context"*. The correct figures are **51 reserved** and **17 contextual**.

D001-R2 reported 52. The cause is reproducible and worth recording: extracting
the reserved list with a regex over the specification text returns 52 matches,
because the block ends with `_ (underscore)` and the gloss word `underscore`
matches the identifier pattern. The prose count is authoritative; the regex count
is not. `REPRODUCIBILITY.md` §9b shows both numbers side by side so the trap is
visible rather than remembered.

### 3.2 Measured behaviour, not inference

| Questionnaire | Measurement | Result |
| --- | --- | --- |
| Does the JVM accept Java keywords as class names? | 71 hand-built class files loaded under `-Xverify:all` | **all 71 accepted**; 68 keywords plus `true`, `false`, `null` |
| Does `javac` accept them as class names? | 71 single-class compilations | **all 71 rejected** |
| Does the JVM accept keywords as method names? | class `Foo` with `static void Foo()` | accepted |
| Can a class be named `java.*`? | `defineClass("java/evil", ...)` | rejected: `IllegalName` |

D001-R2 claimed `javac` rejects only `var`, `yield`, `record`, `sealed`, and
`permits`. That was a five-name probe generalized into a rule. The measured truth
is that `javac` rejects **every** keyword as a class name, so a rule excluding
five names would have permitted `int`, `class`, and `_` as unit names.

### 3.3 The five namespaces

The conflation that produced both errors is now explicit in `semantics.md`
§1.2a. The same character sequence is legal in some namespaces and illegal in
others, and each has its own constraint source:

| # | Namespace | Constraint source | Governs | Example legal here, illegal elsewhere |
| --- | --- | --- | --- | --- |
| A | Arara source identifiers | this specification | functions, locals, params | `record`, `if` — legal function names |
| B | Arara unit names | §1.2b | `.ara` base name | `Foo` — legal; `String` illegal by rule 3 |
| C | JVM binary class names | JVMS 21 §4.2.1 | internal name | `if` — legal as a class file |
| D | Java-source-accessible | JLS 21 §3.8, §3.9 | names writable in Java source | `main` — legal; `int` illegal |
| E | Protected packages | JVM `defineClass` | `java.*` internal names | nothing — no package declarations exist |

The policy that follows:

1. **Prevents verified collisions** by picking the intersection of §1.2 pattern
   and JVMS §4.2.1 for the character set, then excluding names proven to break
   Java source.
2. **Defines deterministic mapping**: unit base name becomes the class's internal
   name verbatim, no mangling, no package prefix.
3. **Prohibits 71 keyword names and 5 shadowing names**, each with a diagnostic —
   `ARA-SRC-0004` and `ARA-SRC-0005` respectively.
4. **Distinguishes** JVM-valid-but-Java-inaccessible (`if` as a class name is
   valid bytecode that `javac` cannot reference) from JVM-invalid (`java/evil`).
5. **Avoids over-restriction**: function and local names are unconstrained, so an
   Arara program may define `fun record()` or a local named `if`. Arara is not
   Java, and the restriction exists only where interop demands it.
6. **Examples** are in §1.2b and §1.5a, with the valid/invalid split stated.

### 3.4 Shadowing, corrected

D001-R2 stated that a unit named `java` breaks `java.lang.String`. It does — in
the **qualified** form only. A Java file using unqualified `String` compiles
unaffected with `java.class` on the classpath, because `String` resolves through
`java.lang` directly rather than through the `java` class.

| Shadowing unit | Java source form | Control | Result |
| --- | --- | --- | --- |
| `String` | `String s = "abc";` | compiles | `incompatible types` |
| `System` | `System.out.println` | compiles | `cannot find symbol: variable out` |
| `Object` | `Integer` returned as `Object` | compiles | `incompatible types` |
| `Math` | `Math.abs(-2)` | compiles | `cannot find symbol: method abs` |
| `java` | `java.lang.String s` | compiles | `cannot find symbol: class lang` |
| `java` | unqualified `String` | compiles | **compiles** — no effect |

Every row has a control that compiles cleanly. Without the control the earlier
result was uninterpretable, which is exactly how the over-broad claim survived
review.
