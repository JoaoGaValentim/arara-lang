## G. Defect found by independent review, and its correction

**One blocking defect was found and fixed before integration.**

`lexical.md` rule 41 states that a string may not continue across lines "not
even with a trailing `\`", and prescribes `ARA-LEX-0203` with recovery that
discards the partial literal and resumes at the break.

The escape branch consumed the backslash and the following character
unconditionally, so a line break immediately after a backslash was never examined
by the raw-break branch. For `"ab\` + LF + `cd"` the lexer produced:

```text
1:4: error [ARA-LEX-0202] invalid escape sequence (1:4-2:1)
```

with a single `STRING_LITERAL` whose span crossed the line break, silently joining
two lines. Three things were wrong: the diagnostic code, the recovery, and the
token stream.

The suite passed while the contract was violated, because no test covered a
backslash immediately before a line break. That is precisely the failure mode
`conformance-plan.md` §1.3 warns about — a test that passes because the compiler
rejected *something* is not conformance.

The fix checks for a line break before decoding the escape, reports
`ARA-LEX-0203` spanning exactly the break, and returns with the position at the
break so the newline is lexed normally. Two regression tests were added: one
asserts the code and span, the other asserts no `STRING_LITERAL` spans the break
and that a `NEWLINE` is produced.

Re-verified unchanged after the fix: all five permitted escapes decode, `\q` is
still `ARA-LEX-0202` with recovery, and a trailing backslash at end of file is
still `ARA-LEX-0201`. **No golden fixture changed**, so the fix corrects behaviour
rather than masking a recorded expectation.

This is recorded rather than quietly repaired because the defect was found by
review of a claimed-complete increment, which is the only reason it was found at
all.

- The read-only agent allowlists were verified against one VS Code and one
