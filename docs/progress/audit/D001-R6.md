`branch` field, commit pins, and publication state refer to
`infra/d001-r4-copilot-migration`, and the merge did not change them. It is not
silently reused as a description of `main`.

Concrete consequences:

- `branch: infra/d001-r4-copilot-migration` is true and remains true. The branch
  still exists at `b0c2492` after the merge; merging does not delete it.
- `last_verified_commit` records a commit on that branch, which is now an ancestor
  of `main` rather than the tip of `main`.
- The ledger's working-tree statement concerns this checkout, not the remote.

This is a **known, disclosed gap**, not a defect of the merge. Reconciling it for
`main` requires a narrowly scoped documentation-only follow-up branch and its own
Draft PR; pushing a corrective commit directly to protected `main` is prohibited,
and the ledger's invariants are not redefined to make the gap disappear.

The acceptance record itself could not be committed to `main` either, for the same
protection reason. It was therefore delivered on the follow-up branch
`docs/d001-r6-acceptance` as **Draft PR #2**, whose reviewed head is
`359e0bd875e23cdbbd6d766c690aae2bac8e7181` and which changes 7 files, all
documentation.

**Correction, Directive 001-R7.** The first version of this section said
`git merge-base main HEAD` is `5441a9f`. That is false. The branch continues from
`b0c2492`, the reviewed tip of PR #1, not from the merge commit:

```text

```

The claim was wrong in a way that mattered, because it implied the branch already

conflict, and the PR reports `MERGEABLE` / `CLEAN`. The ancestry claim is corrected

So the precise post-merge state is: the **foundation** is on `main` and verified;
